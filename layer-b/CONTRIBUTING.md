# Contributing

Open an issue before substantial architectural changes. Include scope/jurisdiction,
source dates, authority versus interpretation versus proposed design, affected B domains,
Layer A constraints, competing explanations and verification plans.

Use synthetic or authorized shareable data. Do not commit credentials, protected records,
personnel case files, vendor secrets or confidential legal material. Do not label anomalies
as misconduct without a properly authorized evidence-based process.

For schema/validator changes include positive and negative tests, preserve stable versions
and explain compatibility. Run the README validation commands and inspect documented exit
codes. Document measurement definitions and counter-metrics; do not invent performance data.
