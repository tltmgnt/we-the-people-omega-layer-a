## Reproducible synthetic workflow

1. Browse/search all 50 workstreams. Each shows missing definitions, current imported-source status, the numbered plan and a dedicated prototype link where available. **Open delivery record** selects the exact project in the original portfolio app. The ten shared projects 041–050 are listed as proposed methods/capstone, never assumed to be validated prerequisites.
2. Enter an identifier and **Import supplied portfolio overview**. This creates an unreviewed, hashed source version in the shared source catalog (`initiative-overview`). It includes all supplied project URLs, the four unassigned foundational URLs and the formula/curriculum references. It does not retrieve any linked document. Review this text separately in the original workspace. Re-importing or changing review metadata makes existing collaboration evidence stale. Once imported, the overview becomes a context dependency for all collaborations in that workspace.
3. Create `SYN-COLLABORATION`, select a bounded participating workstream (for example 009), and optionally shared source dependencies. Record the office-review question, baseline plan, success criteria and counter-metrics, accountable owner, resources, continuity protection and rollback plan. Use `2026-01-01T00:00:00Z` and fictional records. Office questions are stored locally; no office is recommended, contacted or represented as a partner.
4. Add DEPENDENCY `042 → 009` with an explicit rationale and `active=true` only if appropriate to the hypothetical scope. The context now includes project 042 and its prerequisites transitively. Cycles and self-dependencies are rejected. Another record with the same pair and `active=false` deactivates the edge without deleting history. This graph models declared research prerequisites, not legal authority or a claim that institutional relationships cannot contain loops.
5. Record PRIORITY decisions as CANDIDATE, DEFERRED or REQUIRES_DEFINITION, with owner and rationale. These are planning records, not funding or implementation authorizations and do not silently redefine unknown titles.
6. Record STAGE `FRAMEWORK_REVIEW` with owner, evidence and limitations at `2026-01-01T01:00:00Z`. A distinct local identifier must record STAGE CHECK against the exact stage sequence before advancing. Attempting `PILOT_SELECTED` while scope/source/safeguards are incomplete returns explicit blockers.
7. In the delivery workspace, define participating/prerequisite project owners/scopes, import their full authorized or explicitly synthetic source text and review it, then confirm scope against that source. Import clears prior scope confirmation. Review any selected shared sources and the imported initiative overview. Source documents in a fictional test are not real project acceptance.
8. Record all eight SAFEGUARD assertions as MET only with fictional supporting evidence and accountable owner. Use a different identifier for each SAFEGUARD CHECK against its exact current assertion sequence. UNKNOWN, GAP, missing, stale, superseded or failed checks block the rehearsal. Identifiers are not authenticated reviewers or officials.
9. If source/scope/dependency changes made framework review stale, append REOPEN with a reason. This returns the rehearsal to PROPOSED and preserves history. Record and check framework review again, then progress through PILOT_SELECTED → BASELINE_RECORDED → CONTROLLED_TEST_RECORDED → INDEPENDENT_EVALUATION_RECORDED → REPORT_RECORDED. Each prior stage needs a separate passing check; every later stage rechecks definitions, source reviews, safeguards and unanswered challenges. The final report stage also has a separate check indicator.
10. Record CHALLENGE questions with synthetic IDs, owners and evidence; unanswered questions block later gates. RESPONSE records document replies, but a reply does not establish that a rights issue was resolved. Record a fresh challenge for an unresolved/recurrent issue. Reload and export/backup to verify persistence.

No synthetic stage grants permission to conduct a real intervention, obtain protected data, select vendors, sign agreements, publish findings or contact an agency. The names of stages describe recorded scenario evidence only.

## Data, gate and measurement contract

The application stores local fictional records. Required fields reject blanks, unknown keys, invalid types, out-of-order scenario timestamps, stale versions and unknown IDs. Collaboration scope is immutable after registration; create another collaboration for a different bounded scope. Dependencies may evolve through append-only records. Priority decisions do not change scope or automatically implement projects.

Each event pins participating and transitive prerequisite **project versions**, current source revision/hash/reviewer/review timestamp, active dependency sequences and the bundled overview's hash. Any relevant change invalidates earlier context. If imported, the shared initiative overview is also pinned; it remains unreviewed until separately reviewed. Explicit shared source IDs can include foundation/layer/formula/curriculum records. Changes to undeclared sources cannot automatically invalidate work; declare the dependency or review its impact manually.

Before stages after framework review, each scoped project needs a title, accountable owner and source-confirmed scope. Every pinned source must have readable imported content and a current local review. All eight safeguard assertions must be MET, current, and separately checked; latest failed/superseded checks cannot satisfy a gate. Every preceding stage needs an exact, current separate check. A previous stage is never silently reset; REOPEN records the reason for restarting the rehearsal.

Safeguards are authority; rights/accessibility; privacy/security; human accountability; independent challenge; transparency/correction; jurisdiction/Tribal sovereignty; service continuity. Completion here is a local evidence assertion, not an independent assessment of those protections. Original Layer A/legal review remains required even when every synthetic gate passes.

Counts are an inventory, not a performance score: exactly 50 registered workstreams; twelve delivered synthetic domain prototypes; missing project source count depends on the local workspace's imports. They do not measure implementation quality, institutional adoption or causal improvements. Readiness is a list of explicit blockers, not an invented numerical/composite ranking. The collaboration report describes current context; append-only event snapshots preserve old contexts but no historical-report cutoff is implemented.

Keep exports out of public git; entered sources and identifiers may be private. Use loopback and synthetic data only. This is a single-workspace app with a shared mutation token and unauthenticated asserted actors, not a production collaboration platform. It sends no messages, retrieves no private documents and performs no live government operations. The overview software is delivered; the portfolio's substantive research, domain implementations and institutional acceptance remain separate outstanding work.
