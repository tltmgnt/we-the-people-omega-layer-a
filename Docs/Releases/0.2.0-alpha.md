versions remain 0.1.0 because this release introduces them without changing their contracts.

## Merge sequence

The maintainer reviews each change before merging. Prefer merge commits for this stacked
chain to preserve predecessor ancestry.

1. Review and merge PR 1 to main.
2. Retarget PR 2 to main, confirm its diff contains only intended pilot changes, resolve
   conflicts if any and require passing checks on its current head before merging.
3. Repeat for PR 3, then PR 4, then this release-preparation PR, always retargeting to main
   after its predecessor is merged.
4. If squash/rebase merging is required by repository policy, reconcile descendant branches
   with main before continuing; verify the resulting diff and rerun checks. Do not force-push
   shared branches or merge duplicated predecessor changes without inspection.
5. Preserve the branch chain until descendants are safely retargeted. Update the preparation
   snapshot during release review so unmerged work is not represented as shipped.

No merge, tag or publication is performed by this document.

## Acceptance checklist

All items need recorded evidence against the exact final main commit.

- [ ] Maintainer accepts the release scope and confirms the PR chain is merged with intended diffs.
- [ ] All automated tests pass and CI is green on the final main commit.
- [ ] Original and pilot review records validate structurally while reporting BLOCKED.
- [ ] Pilot and exchange readiness checks return 2; unsupported or inconsistent exchanges fail tests.
- [ ] All local documentation links resolve; README and changelog match the delivered inventory.
- [ ] Qualified reviewers assess the proposed domain/gate content and maintainer records findings,
      open limitations and their disposition. No jurisdiction-specific legal validation is claimed.
- [ ] Project owner resolves licensing before inviting public reuse: add the authorized license(s),
      identify code/documentation coverage and third-party exclusions, and update LICENSE-SELECTION.md.
- [ ] Review examples for synthetic-only content and confirm no credentials, case files or sensitive
      personal data have entered the release diff.
- [ ] Fill the evidence ledger below with actual commit, check results, reviewers and decisions.
- [ ] Maintainer explicitly approves creating the release tag and publishing the release notes.

Licensing is a known owner decision, not a license choice delegated to tooling.
A missing approval or unresolved acceptance item means the release remains unreleased.

## Reproduce validation

Use Python 3.12 on a clean checkout of the candidate main commit:

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python scripts/validate_review.py example-review.json pilots/benefits-process/01-intake.json pilots/benefits-process/02-escalated.json
python -m scripts.validate_exchange examples/cross-layer/exchange.json
```

These commands must exit 0; the records and exchange must still print BLOCKED.
Then run each readiness command separately and record its exit code:

```sh
python scripts/validate_review.py --require-ready pilots/benefits-process/01-intake.json pilots/benefits-process/02-escalated.json
python -m scripts.validate_exchange --require-ready examples/cross-layer/exchange.json
```

Both must exit 2. That is the expected hold, not a failed release test. Unexpected readiness,
schema errors or missing files must be investigated rather than ignored.
The current suite has 21 test methods; record the actual count on the final commit.

The [stack review](stack-review-2026-10-31.md) records the preparatory code review and parser fix;
it does not replace qualified content review or final-main evidence.
